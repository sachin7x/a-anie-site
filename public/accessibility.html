What we have done

  • Skip-to-content link on every page, visible on focus. The first interactive element on each page is the skip link, so keyboard users can bypass the nav.
  • Semantic landmarks: <header role="banner">, <nav aria-label="Primary">, <main id="main">, <footer role="contentinfo">. Screen readers can navigate by region.
  • Visible focus rings: the default Bootstrap focus ring is overridden in styles.css to a high-contrast outline, not removed.
  • Color contrast: body text against the cream background (#FDFCE8) uses #131313, well above 7:1. Muted text uses #5a5a5a, above 4.5:1. Link blue is checked against the same backgrounds.
  • Responsive layout: tested at 360px, 768px, 1024px, and 1440px widths. No horizontal scroll on any standard viewport.
  • Mobile nav toggle: the hamburger button is keyboard-reachable, has an aria-expanded state, and the menu traps no focus (it is a simple disclosure).
  • Form labels: every input on the contact and login forms has an associated <label>. Required fields are marked with aria-required and visual asterisks.
  • Reduced motion: no motion runs on the site. The prefers-reduced-motion media query is honored trivially because nothing animates.
  • Language: every page declares html lang="en". Headings form a single h1 per page, with a logical h2/h3 outline below it.

Known gaps

  • No automated scan results published. The site has not been run through axe-core or a Lighthouse accessibility audit on a recurring basis; the developer's manual review is what is here.
  • SVG illustrations have aria-hidden="true" because they are decorative. There is no long description for the few that convey information; if a screen reader user finds one of the illustrations missing, that's a real gap to report.
  • The hero waveform animation on the index page is a CSS keyframe; it is paused under prefers-reduced-motion: reduce but the static frame is decorative. There is no audio description.
  • The desktop app is partially audited: keyboard navigation works, contrast meets AA in light mode, dark mode is in development. Screen reader testing on Windows and macOS is pending. The current app is usable with VoiceOver on macOS for the core flow (record → transcribe → copy).
  • Third-party content: the Wispr Flow demo mirror under /demo is unmodified. Its accessibility is what Wispr Flow shipped; it is not covered by this statement.

Reporting a barrier

If something on this site is in your way, write to the address in /.well-known/security.txt with the subject line starting ACCESSIBILITY. Include the page URL, the assistive technology you are using, the browser, and what you expected to happen. A fix or an honest “won't fix, here's why” reply is the target; the current cadence is best-effort within a working week.

Compatibility we test against

The site is built with progressive enhancement in mind: it works without JavaScript for every page except the form validation, which is progressive enhancement on top of native HTML5 validation. Browsers we explicitly check before deploy are current Chrome, Firefox, Safari, and Edge. Screen readers we have tested with are VoiceOver on macOS and iOS, and NVDA on Windows. If you use something else and find an issue, that is the report we most want.

What will change this page

This page is updated whenever a real change to the site is shipped. The next planned improvement is a Lighthouse accessibility check on every deploy, with the score published on this page. That work is in flight, not done; the day it is done, this page will be rewritten to link to the report instead of describing the manual review.
