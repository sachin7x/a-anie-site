Security & trust, honestly scoped.

Last updated: 3 September 2026 · A-Anie is a solo-built product.

The one-line answer

A-Anie is a voice-to-text desktop app built by one developer in Kishangarh. We do not hold SOC 2, ISO 27001, HITRUST, a bug-bounty program, or a third-party penetration test. We do not have an enterprise sales motion. If your security review requires any of those, this page will not pass it — and that is the honest answer, not a gap we plan to close quietly.

This page exists so that what we do have is documented, what we don't have is named, and how to reach the developer about a security issue is one click away. The structure mirrors the kind of Trust Center a venture-funded competitor would publish — for reference, see Wispr Flow's public privacy page and their full enterprise Trust Center, which includes SOC 2 Type 1 (April 2026), an ISO 27001 letter, and a pen-test remediation report.

What we do, instead

Subresource Integrity on every third-party asset

The marketing site is seven static HTML files served by Vercel. Every external stylesheet and script reference carries a Subresource Integrity (SRI) hash. A previous production incident in which a fabricated SRI hash silently broke the stylesheet is the reason this is checked in code review, not just at deploy time.

Security disclosure address published at /.well-known/security.txt

RFC 9116 compliant. The file lives at /.well-known/security.txt and is the canonical place to send a vulnerability report. It is referenced from the footer of every page on this site.

No third-party analytics, advertising, or session-replay

The site does not run Google Analytics, Meta Pixel, Hotjar, FullStory, Segment, Mixpanel, or any equivalent. No third-party JavaScript loads on the marketing pages beyond the Bootstrap 5 CSS/JS bundle (SRI-pinned) and Google Fonts.

No audio retention

The desktop app processes voice input to produce text and does not store the audio. Transcripts are kept against the user account for the duration of the account; deletion is immediate on account removal. See Data Controls for the full list.

One serverless function, narrow surface

api/contact.js is the only server-side code on this site. It accepts a POST from the contact form, validates that the input is a name + email + short message, and emails the developer. There is no database, no auth, no user state, no admin panel.

No build step, no Node server, no transpiled code in production

Production is the contents of public/ exactly as it sits in the repo. There is nothing to compile, nothing to bundle, nothing that runs server-side other than api/contact.js. This means the production attack surface is what you see in the HTML.

Reporting a vulnerability

Send details to the address listed in security.txt. Include a clear subject line, a reproducible proof of concept, and the impact you observed. Please do not file a public GitHub issue for security bugs.

What happens next, in the order it happens:

  • An acknowledgement within 7 days. If you don't get one, write again — it may have been caught by spam filtering.
  • A triage decision within 30 days: accepted, duplicate, won't fix, or needs more info.
  • A fix on a best-effort timeline. Severity determines the calendar; critical issues are worked on first.
  • Public acknowledgement, if you want one, in the changelog after the fix ships.

No monetary bounty. No SLA in the enterprise sense. No coordinated disclosure timeline. This is what one developer can promise, honestly.

Where we'd start, if we went enterprise

For a reader who is comparing A-Anie to a venture-funded competitor's Trust Center and trying to map the gap: the categories below are the ones a credible enterprise security program would need to cover. They are listed here as the “what it would take” answer, not as claims.

  • Information Security Policy + ISMS Manual — a written, versioned policy set covering access control, data classification, change management, vendor management, incident response, business continuity, and personnel security.
  • Access Control & Termination Policy — who has production access, how access is granted and revoked, MFA enforcement, session policy, principle of least privilege.
  • Data Classification + Data Handling + Data Retention & Disposal — the policy trio that defines what data is sensitive, how it is handled, and when it is destroyed.
  • Change Management + SDLC — how production changes are reviewed, tested, and approved; how source code is reviewed; how dependencies are kept current.
  • Vendor Management + Risk Assessment — how third-party services (Vercel, the STT provider, the payment provider) are evaluated and monitored.
  • Incident Response + Breach Notification — a written runbook, named roles (even if the role is “the developer”), customer notification templates, regulator notification timelines.
  • Asset Management + Baseline Hardening — an inventory of systems, hardened base images, patch cadence.
  • AI Policy — what model is used, what data is sent to it, what is logged, what is retained, how the model is evaluated for the specific use case.
  • Network Security + Password + Physical Security — applicable in different shapes for a hosted SaaS vs. a distributed company, but each is a required section in a SOC 2 audit.
  • Acceptable Use + Personnel Security — what employees (here: the developer) are and are not allowed to do with the systems they have access to.

None of these are written. None are in flight. If you are evaluating A-Anie and need any of them, the right next step is to ask whether your timeline tolerates waiting for them, not to interpret this page as a placeholder that will quietly fill in.
